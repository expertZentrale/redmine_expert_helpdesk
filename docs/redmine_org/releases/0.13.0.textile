h3. Added

* *Signature logos and icons can be blocked once instead of deleted forever.* A business mail carries the sender's signature logo, a row of social-media icons and a tracking pixel, and Redmine's mail handler stores every single one as a real attachment. Ten mails in a thread therefore leave thirty files on the ticket, none of them evidence, and the one screenshot the customer actually sent is buried among them. Every attachment row on a ticket now carries a *Block* button. One click blocks that file for the project and deletes every copy already attached to a ticket of that project — the confirmation names the real number first ("3 attachments are deleted"), which the server counts before it asks. From then on, incoming mail carrying the same file arrives without it.
* *The match is the file content, not the file name.* Outlook numbers embedded images per mail, so @image001.png@ is whatever that sender's client happened to put first: blocking by name would hit a different customer's logo on the next ticket and, sooner or later, a screenshot. Each entry is the SHA-256 of the bytes, so a blocked file is blocked exactly when it is byte-for-byte the same one. A logo that a mail client re-encodes for every mail is deliberately *not* caught — a filter that guesses may lose a logo, never a screenshot.
* *Deleting the file is only half of it.* By the time an agent sees the ticket, the plugin has turned the mail's inline-image references into image markup pointing at the attachment, so removing the file alone would trade a signature logo for a broken image. Every removal therefore also strips the markup that named it, and writes the text past the callbacks: the cleanup produces no journal entry, no "edited" marker and no notification for text the customer wrote.
* *The button is not offered on everything.* Blocking deletes a file from every ticket in the project, so it must not sit next to the evidence. Two settings decide which attachments an agent is shown the button for at all: an allow list of file types (extensions such as @gif@, or MIME types such as @image/gif@ and @image/*@; @*@ allows all) and an upper size limit, defaulting to the image formats logos arrive in and 100 KB. An @.eml@, a @.msg@, a PDF or a log therefore never gets the button, and neither does any image above the limit — which is where screenshots normally sit. The guards bound what the button can reach; they do not classify content, so a small screenshot saved as a PNG is still eligible and the confirmation is the last check. Both are set centrally and can be overridden per project, and both are enforced again on the server, so a page left open since the settings changed cannot bypass them.
* Blocked files are listed under *Project settings → expert Helpdesk → Blocked attachments* with the name and size of the blocked copy, who blocked it, and how often the filter has dropped a file since — so an entry that never earns its keep is visible and can be removed again. Blocking requires the *Manage helpdesk* permission; the project is always taken from the ticket the attachment hangs on, never from a parameter.

h3. Fixed

* *The embedded images of a mail no longer all show the same picture.* Outlook names every embedded image @image.png@, so a mail whose signature carries a logo, a phone icon, a mail icon and four social icons arrives as seven parts with seven content IDs and a single file name between them. Two things then went wrong at once. The parts were matched to the stored attachments *by file name*, so all of them were handed the same file; and the markup written into the ticket was the bare name, which Redmine does not treat as a reference but as a lookup — it resolves the name against every attachment of the ticket and returns the newest match. A ticket that showed nine different pictures in the mail showed the same screenshot nine times over. Parts are now matched by their *content* — the file name narrows the field, then the part's byte count and, if that still ties, its SHA-256 pick the right file, and each part claims its attachment so two parts can never take the same one — and the markup names the download path, which carries the attachment id and therefore means exactly one file.
* *The same fault in the outgoing direction.* When an agent quoted such a mail in a reply, the outgoing image resolution also matched on the file name, so the first candidate claimed every reference and the customer received one picture as many times as the mail had images. References carrying a download path are now resolved by the attachment id; a bare file name still matches a freshly pasted upload, which has no id yet.
* A slower failure is fixed with it, and it did not need duplicate names: a reply's attachments are appended to the *ticket*, and the description is rendered against those, so the next mail carrying an @image.png@ quietly took over the markers of the first — a ticket's description could start showing a later reply's pictures. Sub-URI installations are handled too: the image path now includes the application's URL root, which the previous fallback omitted.

h3. Upgrade notes

Two migrations run on upgrade (057–058). They create the table of blocked attachment contents and add the two guard settings to the per-project settings; nothing is blocked until an agent blocks something, so no existing ticket, mailbox or attachment is touched by the upgrade itself.

No new permission is introduced. The *Block* button follows *Manage helpdesk*, the permission that already covers mailboxes, rules and answer templates.

The defaults for the button guards are the image formats signature logos arrive in (@png, gif, jpg, jpeg, bmp, webp, tif, tiff, ico@) and 100 KB. Both can be changed under *Administration → Plugins → Redmine expert Helpdesk* and overridden per project; leave a project field empty to inherit the central value.

*The inline-image fix applies to mail received from this version on.* Text written earlier keeps whatever its markers resolved to at the time; tickets already showing the wrong picture are not rewritten, because repairing them would mean bulk-editing description and note text on existing tickets.
